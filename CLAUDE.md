# CLAUDE.md

This repository holds **two** products that share one source of truth:

| | Where | What |
| --- | --- | --- |
| Website | repository root | Hugo site published to `docs/`, served by GitHub Pages at bhagwadgita.info |
| Native app | `app/` | SwiftUI reader for iPhone, iPad and Mac — **see `app/CLAUDE.md`** |

Both derive from `srimad.csv` **and** `enriched.sqlite` (generated by
`tools/enrich.py`, see Tooling below). The site used to be the CSV alone; a
verse page now carries the same blocks the app shows, out of the same database,
and `tools/build_db.py` holds the repairs both of them apply to it.

The rest of this file is the **website**. For anything under `app/`, read
`app/CLAUDE.md` first — it is the authority on how that code is written.

---

Static site for **bhagwadgita.info** — all 701 verses of the Bhagavad Gita with the
original Sanskrit plus Hindi and English translations/commentary. Built with Hugo,
hosted on GitHub Pages.

## Stack

| Piece | Choice |
| --- | --- |
| Generator | Hugo (extended), currently building on v0.165.0 |
| Theme | `themes/book` — local, hand-written, **not** a git submodule |
| Content source | Scraped from gitasupersite.iitk.ac.in by `main.py` |
| Hosting | GitHub Pages, serving the `docs/` folder on `master` |
| Domain | `bhagwadgita.info` via `CNAME` |

## Layout

```
config.toml            site config; note publishDir = "docs"
content/
  chapter-1..18/       sutra-N.md — one file per verse, 701 total
data/
  chapters.toml        chapter names (Sanskrit + English), keyed "1".."18"
static/
  CNAME                custom domain, copied into docs/ on every build
docs/                  BUILD OUTPUT — committed to git, this is what Pages serves
themes/book/
  layouts/
    index.html         homepage: chapter/verse directory
    _default/
      baseof.html      shell for every page, including the homepage
      single.html      one verse
      list.html        chapter index (/chapter-N/)
    partials/          head, header, footer, sideNav, burger, pagination,
                       analytics, schema, rail (the app's own menu: themes,
                       text size, jump-to-verse, verse-detail switches)
    shortcodes/
      lines.html       a block whose line breaks are part of the text
  assets/              css/main.css, js/main.js — piped through minify+fingerprint
  static/              krishna.png (og:image), krishna-300.png (footer),
                       favicon.ico + apple-touch-icon.png (the app's mark)
main.py                scraper + content generator (see below)
srimad.csv             scraped raw data, the intermediate the generator reads
publish.sh             build + commit + push in one shot
```

### Content model

Every verse file carries the front matter the templates group on:

```yaml
title: "Verse: 1,1"
chapter: 1     # int — templates select on this with `where`
sutra: 1       # int — ordering within a chapter, `sort ... "Params.sutra"`
position: 1    # global running counter
```

`chapter` and `sutra` must stay integers. The nav, homepage directory, and chapter
lists all sort and group on them; a stringified value silently sorts wrong.

The body is fixed-shape Markdown, and the shape has three kinds of block. Keep
it — `css/main.css` and the gear menu's switches are both written against it.

| Section | Source | Rendered as |
| --- | --- | --- |
| मूल श्लोक | `enriched.sqlite`, through `build_db.normalize` | `{{< lines >}}` |
| Hindi Translation By Swami Ramsukhdas | `srimad.csv` | fenced block |
| Hindi Commentary By Swami Chinmayananda | `srimad.csv` | fenced block |
| English Translation By Swami  Sivananda | `srimad.csv` | fenced block |
| Transliteration | `enriched.sqlite`, through `align_transliteration` | `{{< lines >}}` |
| अनुवाद, भावार्थ | `enriched.sqlite` | prose |
| Translation, Meaning | `enriched.sqlite` | prose |
| शब्दार्थ, Word by word | `enriched.sqlite` | Markdown table |

Note the two spaces in "Swami  Sivananda" — the scrape's, and load-bearing:
`main.js` maps headings to switches by exact text.

**Fenced blocks are prose that merely arrived pre-wrapped**, and must be free to
re-wrap; the shloka and its transliteration are composed in lines, and where a
line ends is part of the verse. That is what `{{< lines >}}` marks. It used to
be inferred from position (`pre:first-of-type`), which was true only while the
shloka was the sole block of its kind — adding the transliteration below it
collapsed the IAST into one paragraph.

The last eight sections only exist for a verse the enrichment has reached, and
print nothing at all for one it has not.

### Regenerating content

`main.py` has two entry points:

- `crawl()` — hits the IIT Kanpur Gita Supersite, scrapes each verse, appends rows to
  `srimad.csv`. Slow and network-dependent; only rerun if the source data changes.
- `main()` — the default when you run the script. Reads `srimad.csv` and rewrites
  every `content/chapter-N/sutra-M.md`. This is the safe, offline path.

`main()` **overwrites** the whole `content/` tree, so hand edits to verse files are
not durable — fix `srimad.csv` (or the template inside `main.py`) instead.

Only `crawl()` needs `requests` and `beautifulsoup4`, and it imports them itself
rather than at module scope — regenerating `content/` is the path everyone
actually runs, and it has no business failing on a checkout that never installed
a network stack it does not use. So `python3 main.py` works with no venv at all.
For the scraper:

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install requests beautifulsoup4
```

`main.py` imports `normalize` and `align_transliteration` from
`tools/build_db.py` rather than repeating them. Those two repairs — splitting a
speaker's name off the first word it is fused to, and unescaping a literal
backslash-n in the IAST — are the difference between the site and the app
printing the same verse. The site skipped them for as long as it had its own
copy of the logic, which is to say: do not grow a second copy.

### Social share cards

`tools/make_og_images.py` renders one 1200×630 JPEG per verse into
`themes/book/static/og/<chapter>-<sutra>.jpg`, plus `og/default.jpg` for the
homepage. `head.html` points `og:image` / `twitter:image` at the matching card, so
pasting a verse link into WhatsApp, Twitter/X or Telegram previews that verse
specifically — chapter name, verse number, the shloka, the English translation and
the domain.

```bash
.venv/bin/pip install Pillow
.venv/bin/python tools/make_og_images.py     # ~700 cards, about 40 MB
```

It reads `srimad.csv`, **not** `content/` and not the database — so a card shows
the scrape's own wording where the page above it shows the enriched shloka. The
two differ visibly on the 28 verses whose speaker attribution the page splits
onto its own line. Worth fixing by pointing it at `enriched.sqlite` through the
same `build_db.normalize`; nothing depends on it staying as it is.

Only rerun it when verse text or the card design changes; the output is committed
like any other static asset. Two constraints:

- Pillow **must** be built with Raqm (`PIL.features.check("raqm")`), otherwise
  Devanagari conjuncts render as broken glyph sequences. The script refuses to run
  without it.
- It reads Devanagari and serif faces from macOS system font paths. On another OS,
  repoint `DEVA` / `LATIN` / `LATIN_BOLD` at the top of the script.

`krishna.png` is gold line art on an **opaque black** field with no alpha channel —
the watermark mask is built from luminance, not from alpha or an inverted mask.
Both of those stamp a visible rectangle.

## SEO

Handled in `partials/head.html` and `partials/schema.html`:

- Per-page `<title>` and `<meta description>`; verse descriptions are built from
  that verse's English translation, so no two of the 701 pages are duplicates.
  It is cut at the next heading — without that it runs on into the sections
  below it, and the snippet a searcher reads ends mid-transliteration.
- `rel=canonical`, plus `rel=prev` / `rel=next` across the verse sequence.
- JSON-LD: `WebSite` + `Book` on the homepage, `Chapter` + `BreadcrumbList` on
  every verse.
- Per-page Open Graph / Twitter card images with explicit width and height.
- `robots.txt` (`themes/book/layouts/robots.txt`) pointing at the sitemap, and
  `disableKinds = ["taxonomy", "term"]` so empty tag/category pages are not built.
- The site name is the `<h1>` only on the homepage; verse and chapter pages use
  their own heading, which is what a crawler expects.

## Build and release

The output directory `docs/` is **committed to the repository** — GitHub Pages is
configured to serve `master` / `docs`, so a build artifact landing in a commit *is*
the deploy. There is no CI; nothing else publishes this site.

Normal release:

```bash
./publish.sh                 # or: ./publish.sh "custom commit message"
```

which is exactly:

1. `hugo --minify` → writes into `docs/`
2. `git add .` → stages content **and** the regenerated `docs/`
3. `git commit -m "rebuilding site <date>"`
4. `git push origin master` → GitHub Pages picks it up within a minute or two

Consequences worth knowing:

- **Every content change needs a rebuild in the same commit.** Editing `content/`
  without running Hugo changes nothing on the live site.
- Diffs are large and noisy — one verse edit can touch hundreds of files in `docs/`
  because the side nav is baked into every page. That's expected, not a mistake.
- Hugo does not delete unknown files from `docs/`. Stale output from older builds
  lingers (e.g. `docs/page/`, left over from a pagination scheme no longer used).
  Remove such directories by hand when you notice them.
- `publish.sh` ends with a stray `cd ..` — harmless, but it means the script assumes
  it is run from the project root.

Local preview:

```bash
hugo server -D          # http://localhost:1313
```

## Gotchas

- **The theme is vendored, not a submodule.** There is no `.gitmodules`; edit
  `themes/book/` directly and commit it like any other source.
- **Never group verses with `GroupByParam`.** It only groups *string* params, and
  `chapter` / `sutra` are written as ints by `main.py`. It returns zero groups
  silently — which is exactly how the side nav and the homepage directory came to
  render completely empty after Hugo was upgraded. Select with
  `where site.RegularPages "Params.chapter" $n` instead.
- `sideNav.html` is rendered through `partialCached` with **no variant**, so it is
  built once and shared by all 742 pages. It must therefore never reference the
  current page — the "you are here" highlight is applied at runtime in `main.js`
  from `location.pathname`.
- `css/main.css` and `js/main.js` live in `themes/book/assets/`, not `static/`, so
  they go through `minify | fingerprint`. Their published filenames contain a
  content hash; do not link to `/css/main.css` directly.
- The drawer animates `transform`, never `width`. Animating width relayouts ~700
  links per frame, which is what made the original slide-in stutter.
- Analytics is off. `partials/analytics.html` emits nothing unless
  `googleAnalytics` is set in `config.toml`; paste a GA4 measurement id there
  (`G-XXXXXXXXXX`) to turn it on. It used to be a hardcoded UA property, which
  stopped collecting in 2023 and spent three years loading a script that
  recorded nothing.
- **Hugo does not delete unknown files from `docs/`.** `docs/page/`, `docs/tags/`
  and `docs/categories/` sat there from earlier builds until they were removed
  by hand — and because nothing rebuilds them, they went on serving the old
  tracking tag after it had been taken out of every live page. Stale output here
  is not inert; it is a page that is still being served.
- The drawer sits at `left: 0` **under** the rail, not beside it, and clears it
  with `padding-left` instead. Offsetting `left` puts a `calc()` holding both a
  percentage and a custom property inside the closed `translate3d`, and the
  drawer then never opens.

## Tooling (`tools/`)

Three scripts, all offline-safe except `enrich.py`:

| Script | Reads | Writes |
| --- | --- | --- |
| `build_db.py` | `srimad.csv`, `data/chapters.toml`, `enriched.sqlite` | `app/.../gita.sqlite` |
| `enrich.py` | `gita.sqlite` | `enriched.sqlite` (calls the Gemini API) |
| `make_og_images.py` | `srimad.csv`, `krishna.png` | `themes/book/static/og/*.jpg` |
| `make_favicon.py` | the app's `AppIcon.appiconset` | `favicon.ico`, `apple-touch-icon.png` |

`build_db.py` is the one to rerun after any content change — it is deterministic,
takes seconds, and rewrites the app's bundled database from scratch. It also
normalises the shlokas: strips every danda and the trailing `।।chapter.verse।।`
marker, splits speaker attributions onto their own line, and joins lines with
`\n`. Punctuation is presentation and is added back by the app.

`enrich.py` **costs money**. Read the header before running it:

- Default model is the cheapest that does the job, and `--thinking low` is the
  default. A Pro run must be asked for explicitly.
- Reasoning tokens are billed at the output rate but are **not** in
  `candidates_token_count`. Budgeting from visible tokens alone under-reports
  real spend several-fold — chapters 1-5 cost £10 against a reported ~£2. The
  script now counts `thoughts_token_count` and prints an estimated cost.
- It is resumable: finished verses are skipped, so an interrupted run loses
  nothing. Always test on `--limit 1` and inspect with `--show C S` first.
- Model availability differs per API project. `models.list()` advertises models a
  given key cannot actually call — the only honest check is a real request.

## Working on this repository

- **Never run a command that produces no console output.** A silent
  `xcodebuild`, test run or script cannot be distinguished from a hung one. Pipe
  through something that streams progress, and if nothing has appeared in a
  minute, check whether the process is alive (`ps aux`, and whether the log file
  is still growing) rather than waiting.
- `timeout` does not exist on macOS — a command prefixed with it fails with
  `command not found` and never runs, silently succeeding from the shell's point
  of view.
- Run the app's tests before committing, not alongside committing. Chaining
  `test && commit` has already produced one commit with a red suite.
